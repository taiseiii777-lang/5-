AI-Driven School / 月次課題 第4回

何を・どこに保存するか

セキュリティトレンド・デスクのデータ保存設計 — grill-me で整理した内容を図解

SECTION 1

自分の言葉での説明（発表用）

記事本文はニュースや RSS から取る想定なので、DB には載せない。
DB に載せるのは自分が足した情報 — 示唆メモと未読/既読だけ。
記事マスタや AI コメントの型はリポジトリに残し、AI と設計を共有しやすくする。
SECTION 2

保存設計の軸 — 2つの情報源

「誰が作ったデータか」で分けると、保存先の理由が自然に説明できる

自分が足した情報

  • 示唆メモ → Neon DB（user_memos）
  • 未読 / 既読 → Neon DB（user_article_reads）
⇄

ツールが持ってくる情報

  • 記事マスタ（将来 RSS） → リポジトリ（mock-articles.ts）
  • AI コメント・要約・X 反応 → リポジトリ（article-*.ts）
  • 企画・設計メモ → リポジトリ（docs/）
なぜ DB に記事を入れない？ 記事の「正」はニュース/RSS 側。DB に複製すると更新のたびに同期が必要になり、今の用途（自分1人のメモツール）では不要な複雑さになる。
SECTION 3

データ一覧 — 何を・どこに・なぜ

データ 保存先 理由
示唆メモ DB（user_memos） 自分が書いた記録。リロード・別端末で消えてはいけない
未読 / 既読 DB（user_article_reads） 一覧フィルタと連動する自分の状態
記事マスタ リポジトリ（将来 RSS） 正はニュース/RSS 側。DB に複製しない
AI コメント・要約 リポジトリ 設計・型として AI と共有しやすい
企画・設計 リポジトリ（docs/） 開発時の説明資料
SECTION 4

データの流れ — 記事を読んでメモするまで

ニュース / RSS （将来）
→
リポジトリ 記事15件（今はモック）
→
4ペイン UI 読む・フィルタ
→
自分の操作 メモ入力・既読
→
Neon DB 永続保存

記事 ID（article_id）でリポジトリの記事と DB のメモ・既読を紐付ける。 将来 RSS を入れても、同じ ID さえ揃えれば DB のデータはそのまま使える。

SECTION 5

DB に入るもの — テーブル2つ

user_memos（示唆メモ）
列説明
user_id将来の認証用（今は default）
article_id記事 ID
contentメモ本文
updated_at最終更新日時
user_article_reads（既読）
列説明
user_id同上
article_id記事 ID
read_at既読にした日時

なぜ2表に分けたか

  • メモは長文・編集頻度高 → 1記事1行で上書き保存（upsert）
  • 既読はフラグ＋日時 → 記事を選んだときに1行追加
  • 将来「メモだけエクスポート」などしやすい
SECTION 6

例外 — DATABASE_URL がないとき

.env.local なし DATABASE_URL 未設定
→
画面は起動する 記事はリポジトリから表示
→
メモ・既読は消える リロードでリセット
だから「リロード後も残す」データだけ DB に入れる、という線引きが意味を持つ。 Vercel + Neon をつなげば、公開 URL でもメモが残る。
